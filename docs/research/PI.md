# Research: Pi Harness

> **Relation to Vi-Harness:** Primary comparison target. Pi is the control condition in the harness-as-independent-variable experiment.

## What Pi Is

Pi is the harness used in Cognition's Devin and related coding-agent systems. It represents the dominant paradigm for LLM-based coding agents: a structured conversation loop in which the model's responses and tool call outputs are accumulated into a growing message history.

This document describes Pi's architecture as it is relevant to benchmarking against Vi-Harness. It does not attempt a complete reverse-engineering of Pi internals.

---

## Pi's Execution Model (as understood from published behavior)

### Context management

Pi manages context as a conversation transcript. Each iteration appends:
- The previous model response (ASSISTANT turn)
- Each tool call result (TOOL turn or USER continuation)

Context grows at O(N) per iteration. When context approaches the model's limit, Pi applies a compaction heuristic: it keeps the last K turns verbatim and replaces earlier turns with a generic summary generated by a secondary model call.

**Growth rate:** O(N) linear, subject to periodic compaction.

**Compaction loss:** The generic summary does not preserve architectural decisions, security constraints, or specific error signatures with the same fidelity as the original content.

### Termination

Pi terminates on:
- Maximum turn count.
- Model-emitted stop token or explicit completion signal.

Pi does not independently detect oscillation, exact repetition, or trajectory cycles. A model that repeats the same failing tool call 15 times will consume the full turn budget without diagnostic classification.

### Success verification

Pi treats the model's final response as the completion signal. If the model outputs text indicating task completion, the run is marked successful regardless of whether tests pass.

**Impact:** An LLM can produce a false-positive benchmark pass by generating plausible-looking code and stating "task completed" without running or passing tests.

### Security

Pi relies on prompt instructions to constrain model behavior. System prompts include directives like "do not delete files outside the repository."

**Impact:** A model under prompt injection from malicious repository content may disregard these instructions. There is no out-of-process policy boundary.

## What Vi-Harness Takes from Pi

1. **The benchmark adapter interface.** `HarnessExecutionResult` field names (`success`, `finalState`, `changedFiles`, `finalDiff`, `tests`, `iterations`, `modelCalls`, `tokens`, `estimatedCost`, `duration`, `terminationReason`) are deliberately Pi-compatible. This allows a direct, field-for-field metric comparison between the two systems.

2. **The insight that a harness is a first-class engineering concern.** Pi demonstrated that the structure of the runtime loop — not just the model — significantly affects task outcomes. Vi-Harness takes that observation seriously.

3. **Turn-based execution as the natural unit.** The iteration = one turn intuition is preserved, though Vi-Harness extends it to allow multiple tool calls per turn.

## What Vi-Harness Does Differently

| Dimension | Pi | Vi-Harness |
|---|---|---|
| Context strategy | Transcript accumulation + periodic compaction | Compiled per-iteration from scored `ContextObject` graph |
| Context growth | O(N) linear | Sublinear (budgeted, deduplicated, compressed) |
| Success criterion | Model self-report | Empirical `VerificationResult` with exit codes |
| Termination | Max turns or stop token | 14 structured stop conditions |
| Security | Prompt instructions | Out-of-process deny-first `PolicyEngine` |
| Oscillation detection | None | `LoopFingerprint` hash comparison |
| Regression detection | None | Baseline-vs-current check comparison |
| Workspace isolation | Direct mutation | Git baseline capture + agent delta tracking |
| State visibility | Implicit in conversation | Explicit `AgentPhase` state machine |

## How Pi Is Represented in Vi-Harness Benchmarks

The `PiHarnessAdapterRunner` (`src/infra/eval/pi-harness-adapter-runner.ts`) wraps a Pi harness execution and translates its output to `HarnessExecutionResult`. This adapter enables the `DefaultBenchmarkRunner` to run both harnesses against the same `BenchmarkTask` and collect results in a common format.

**Status of live comparisons:** No live benchmark runs exist yet. The Pi vs Vi-Harness comparison is a planned experiment. See [`experiments/PI_VS_VI.md`](../experiments/PI_VS_VI.md).

## Open Questions

1. Does Pi's compaction strategy preserve critical architectural constraints with sufficient fidelity for long-horizon tasks?
2. At what iteration count does Pi's O(N) context growth begin degrading task performance (via truncation or model confusion)?
3. Does Vi-Harness's compilation overhead (per-iteration latency cost) outweigh the quality improvement at short task horizons (< 10 iterations)?
